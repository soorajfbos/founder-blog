## A Founder Checklist for Evaluating Any Software Quote

This pulls together the practical checks worth running before you commit money to a build. Twenty minutes with this list prevents most of the expensive mistakes.

### Before You Request Quotes

- Write a one page brief: problem, user, success number, three must-haves, five exclusions
- Send the identical brief to every supplier
- Decide your maximum spend before seeing any product in real use
- Write down what would make you stop

Different briefs produce incomparable quotes. One brief makes the comparison meaningful.

### Checking the Breakdown

Every quote should show hours or days by category:
- Discovery and design
- Feature build
- Testing and bug fixing
- Infrastructure and deployment
- Documentation and handover
- Contingency, shown separately

If feature coding is more than about half the total, something is missing or hidden.

### Checking the Assumptions

Ask for them in writing. Look for:
- Designs provided by you
- Third party APIs working as documented
- Feedback within a set number of days
- A limited number of revision rounds

Wrong assumptions are the main cause of overruns. Read these before the total.

### Checking What Is Excluded

Confirm whether these are in or out:
- Data import and export
- Error handling and empty states
- Analytics and monitoring
- Admin tools
- Security basics and access control
- Post launch bug fixing

Add any missing items back at a fair estimate before comparing prices.

### Checking Ownership

Non-negotiable in any agreement:
- Code in your repository from day one
- Accounts and domains in company names with your billing
- IP transfers on creation, not on final payment
- Subcontractors covered by the same terms
- Full admin access throughout

### Checking the Delivery Rhythm

- A clickable demo every week, not a status report
- A named engineer you can speak to directly
- Written weekly update: shipped, next, blocked, risk
- A midpoint checkpoint with the right to cut scope

### Checking the Commercial Terms

- No more than 30 percent upfront
- Payments tied to deliverables, not dates
- Phases with clean exit points
- Change requests in writing with cost and time impact
- Defined warranty period and what counts as a bug

### Checking the Handover

The deliverables list must include:
- Code with full commit history
- Setup instructions tested on a clean machine
- System map and data model
- Runbooks for deploy, rollback, and restore
- Vendor list with costs and purpose

Anything not written down will not be delivered.

### Questions Worth Asking Every Supplier

- What is the riskiest part of this project
- What would you cut if the budget were halved
- How much contingency is in this number
- Who reviews the code
- Could another team pick this up in two weeks

The last question is the most important.

### The Five Mistakes That Cost Most

1. Comparing totals without normalising scope
2. Accepting a quote with no written assumptions
3. Not owning code and accounts from day one
4. Spending the entire budget on the build with nothing held back
5. Waiting more than two weeks to see working software

### The Standard to Hold

Whatever you spend, the result should be a system your company owns, that is documented, that another engineer could maintain, and that handles customer data safely.

That is the same standard applied in a [technical due diligence startup](https://foundersbar.com/articles-and-research/why-software-development-quotes-arent-dropping) review, and holding suppliers to it from the first contract means you never have to scramble later.

### Start Here

Print this list. Work through it with each quote. The supplier who scores best is rarely the cheapest and almost never the one who agreed with everything you said.
